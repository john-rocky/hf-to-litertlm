# Bonsai 2 27B (PrismML ternary Qwen3.8-27B) -> LiteRT-LM — findings

Started 2026-09-19. Everything below was measured in this directory; the scripts are the record.

## What the model is (HF API + pack contents, 2026-09-19)
- Collection `prism-ml/bonsai-2` = one model: **Ternary-Bonsai-2-27B**, base `Qwen/Qwen3.8-27B` (`model_type qwen3_5` = the Qwen3.5 GatedDeltaNet hybrid we already convert: 64 layers = 48 linear-attention + 16 full-attention, hidden 5120, inter 17408, vocab 248,320, untied head, ctx 262K). Apache-2.0. GGUF 405K DL in 3 days; MLX 5K.
- Weights: ternary g128 (one fp16 scale per 128 inputs) on every linear **and the embedding and lm_head**; stored in a **rotated basis** (block-1024 normalized Sylvester Walsh-Hadamard with explicit ±1 signs per width, folded into the weights; the runtime applies `x -> H_1024 (x * s) / 32` to each rotated linear's input and the inverse to the embedding output). `hadamard.json`: 401 forward names + embed_tokens inverse, sign widths 5120 / 17408 / 6144.
- No unpacked release. Exact source = the MLX pack (`Ternary-Bonsai-2-27B-mlx-2bit`, 8.6 GB): affine 2-bit g128 with `bias = -scale`, codes {0,1,2} -> {-s, 0, +s} (q==3 never occurs; 32.8 % of language weights are exactly 0). `runtime/codec.py::unpack` documents the bit order (16 codes per uint32, LSB-first, element = 16*word + lane).

## Recipe (what worked)
1. **Dequant to an HF bf16 checkpoint** (`dequant_mlx_pack.py`, 49 s, ~1 GB RAM, 50 GB out): rotated ternary values kept verbatim (exact in bf16: ±s with s fp16). Three layout traps, all found by the oracle gates below:
   - mlx `Conv1d` weight is `[out, kernel, in]` -> torch `[out, in, kernel]` (transformers refuses the load otherwise).
   - **transformers' `Qwen3_5RMSNorm` computes `x_norm * (1 + w)`; the mlx pack stores mlx's plain `w' = 1 + w`** (mlx_vlm's `sanitize` adds 1 on HF->mlx). Subtract 1 for input/post layernorms, the final norm, q_norm, k_norm. The gated norm (`linear_attn.norm`) is plain in both. Missing this gave "\n\n<|im_end|>" as the greedy answer with per-module parity still perfect (trunc-1 layer corr 0.976 -> 0.999998 after the fix).
   - GDN v-head order: mlx_vlm expands k/q with `mx.repeat` (= `repeat_interleave`, k-head-major) like HF, and the pack is already in that order (`gdn_v_grouped: true`) — no permutation needed.
2. **Oracle = PrismML's own runtime** (`runtime/vision_artifact.py` + mlx-vlm 0.6.3 / mlx 0.32.0, venv `~/venvs/bonsai2mlx`): `mlx_ref.py` vs `hf_check.py` — first-step top-5 logits within 0.05, greedy "Paris<|im_end|>" identical; `parity_hf.py` per-module rel err 1e-3 (fp16 activations on the mlx side); `mx.hadamard_transform` == Sylvester matrix matmul (diff 4e-7).
3. **Export** = the Qwen3.5 hybrid lane (`qwen35_work/litert-torch-qwen35` = litert-torch 115a136 + `qwen35_hybrid_litert_torch.patch`, venv `ltconv040dev`) + `hadamard_export.py` wrapping the 401 rotated linears and the embedding at load time (`export_driver.py` monkeypatches `export_lib.load_model`): the transform lowers to `MUL(sign const) -> RESHAPE(-1,1024) -> FULLY_CONNECTED(H/32, fp32) -> RESHAPE`; the converter CSEs the shared-input rotations (qkv+z, q+k+v, gate+up), 18 rotation FCs in the decode graph. `--experimental_lightweight_conversion` (resource constants, tflite streamed to disk) and `package_model` skipped (a 108 GB fp32 .litertlm is pointless).
4. **Quantize + pack** (`build_bundle.py`): ai-edge-quantizer 0.8.0, int4 BLOCKWISE_32 min-max on every FULLY_CONNECTED (exact container for ternary: {-s,0,+s} -> {-7,0,+7}), int8 channelwise on lm_head (regex `lm_head`, 1 vocab buffer) and the embedding lookup, **the rotation FCs left float via `NO_QUANTIZE` on regex `Linear_hadamard_rotation`** (the first attempt used `(?i)hadamard`, which also matched the wrapper class name `HadamardLinear_*` and left every linear fp32 — check the buffer census, not the file size). Then litert-lm-builder 0.15 pack, zero-scale in-place fix, ExecutorMetadata (state buffers), `prefer_activation_type fp32`.

## Chat template / thinking (tested on the Qwen3.5-0.8B int4 test bundle, litert-lm 0.17.1, 2026-09-19)
- The official 170-line Bonsai 2 / Qwen3.8 template (`|trim`, `namespace`, `is string/iterable/mapping`, macros, `reasoning_effort`) packs and renders on the runtime's minijinja: single-turn `run` and a two-turn Python-API conversation (assistant-history branch) both render without a template error (`multiturn_test.py`). No `.strip()`-class rewrite needed (unlike the gen-1 Bonsai 1.7B template in July).
- Thinking is ON by default in that template (`<think>\n` opener). With `channels { channel_name "thought" start "<think>" end "</think>" is_reasoning_channel true }` + `supports_thinking: true` in LlmMetadata the CLI shows `[thought] … [/thought]` and `--thinking-budget N` is honoured (mechanism check; the 0.8B rambles). Two bundle variants are therefore one `build_bundle.py --prequantized --channels --template <official>` repack apart: (A) simple ChatML, thinking off (gates / GSM8K parity vs the MLX oracle in the same mode) and (B) official template + thought channel (PrismML's benchmark mode).

## 27B int4 bundle (`build_bundle.py`, 2026-09-19 12:52–12:59)
- ai-edge-quantizer 0.8.0 on the 108 GB float tflite via mmap: parameter generation 4 min 13 s (273,844 items), 326 s to the quantized tflite; build RSS peaked ~82 GB; total 418 s to the finished bundle. **`Ternary-Bonsai-2-27B_mixed_int4_b32.litertlm` = 16.46 GB** (int4 blockwise-32 on all 401 rotated linears + the small a/b projections, int8 embedding + int8 lm_head = 2 × 1.27 GB, 18 fp32 rotation FCs of 4 MB). Zero-scale fix found **0** all-zero blocks (the rotated basis has no dead 32-blocks). 128 state buffers (96 linear-attention, 32 KV). Buffer census (`buffer_census.py`): 128 × [17408,5120] + 64 × [5120,17408] + 48 × [10240,5120] + 16 × [12288,5120] int4 — every weight once; the last (attention) layer's q/o/MLP live only in the decode graph because prefill never needs them (dead-code elimination, not duplication).
- Variant B = same tflite repacked with the official template + thought channel (`--prequantized --channels`, sampler top-k 20 / top-p 0.95 / temp 1.0 = PrismML's thinking defaults).

## Gates on `Ternary-Bonsai-2-27B_mixed_int4_b32.litertlm` (litert-lm 0.17.1, Mac M4 Max, 2026-09-19 13:0x–)
- 8-question sanity gate (`qwen35_work/gate8q_qwen35.py`): **CPU 8/8 PASS, GPU (WebGPU) 8/8 PASS**, 0 degenerate. Answers: 42 / Tokyo / Cold / 7 / Merci / 56 / 0.9 / blue.
- b128 variant built from the same float export: `Ternary-Bonsai-2-27B_mixed_int4_b128.litertlm` **15.32 GB** (one fp16 scale per 128-group = the pack's native grouping; also exact for ternary).
- Multi-turn (Python API, cpu): 42 → 84 (context carried; simple template).
- **Logits parity vs the MLX oracle on the full 27B** (`parity_logits_bigmodel.py lt`, CompiledModel CPU decode walk over the 24-token capital-of-France prompt, `full_mlx.npz`): **top-1 24/24, mean KL 0.0002, mean Pearson 0.99988, max |logit diff| 0.316** (int4-b32 + dynamic int8 activations + fp32 Hadamard vs 2-bit + fp16 activations).
- `litert-lm benchmark` 0.17.1, `-p 256 -d 256 --runs 2 --cache no`, Apple M4 Max (137 GB): **CPU prefill 14.6 tok/s, decode 4.79 tok/s, init 313 s, TTFT 17.8 s; GPU (WebGPU) prefill 133 tok/s, decode 14.2 tok/s, init 443 s (shader compile + upload, no cache), TTFT 2.0 s.** Init dominates a cold start; the default `--cache disk` writes a compile cache next to the file for the next load (not measured yet).
- Thinking variant smoke (CPU, `--thinking-budget 600`, train-speed word problem): `[thought] … Speed = 90 km/h … 90*2.5 = 225 km … [/thought]` then `225` — the thought channel and the budget work on 0.17.1; 4 min 9 s wall including the 313 s CPU init.
- **Same-engine multi-conversation GSM8K is invalid for this family (re-confirmed on the 27B, 2026-09-19 14:0x):** `gsm8k_litertlm_api.py` (one GPU engine, a fresh conversation per question) scored 3/21 — the first 3 questions right, then prompt echoes, repetition loops and truncated instruction paraphrases (`gsm8k_lt_b32_gpu_FAILED21.jsonl`). The same questions on a FRESH engine answer normally (`probe_q.py`: q19 GPU 7 ✓ / CPU 7 ✓, q4 GPU 540 ✓, CPU 18 ✗, q21 GPU 29 ✗, CPU "<number>" ✗ — single-question noise between backends, no echo/loop). Cause = the cross-conversation cache dedup rewinding the step but not the linear-attention state (engine-crossconv-dedup-linear-state). Evaluation must be one process per question (`gsm8k_litertlm_cli.py`).
- b128 variant: 8Q **CPU 8/8 PASS** (same answers). GPU 8Q pending.
- GPU init with the runtime's on-disk compile cache (`--cache disk`): first run 276 s, second run 253 s — the cache (3.3 GB program + 14.7 GB weight + 15 GB xnnpack files next to the bundle) does not make a cold process cheap; one fresh process per question is ~4.5 min of init on either backend, so a hermetic n=100 GSM8K costs ~8 h. Caches deleted.
- Same-engine contamination is cumulative and a unique per-conversation system message does not avoid it (`probe_dedup.py`, one GPU engine: q4 540 ✓, q4 540 ✓, q19 2.33 ✗, q4 360 ✗, then with nonce system messages q4 60 ✗, q19 84 ✗, q4 2 ✗ rambling 2915 chars). The engine exposes `create_session` (run_prefill/run_decode) but no state reset. Hermetic = one process per question.
