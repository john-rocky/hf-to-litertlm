# A NaViT-style vision tower on LiteRT-LM's fixed-grid image path

LiteRT-LM 0.18.1's `fast_vlm` model type (and `generic_model` with `image_enabled`) stretches every picture to the file's G × G size and hands the vision encoder `float(u8) * (1/255)` in NHWC, with no mean or standard deviation. A tower written for variable resolutions (Qwen2-VL-style smart_resize, 2D rotary positions, patches ordered by merge block) runs on that path once it is re-written for one fixed grid. These are the steps and checks from LiquidAI/LFM3-VL-2B (`lfm3vl_work/tools/lfm3_vision.py`, the vision graphs of [litert-community/LFM3-VL-2B-LiteRT](https://huggingface.co/litert-community/LFM3-VL-2B-LiteRT); the REPRODUCE.md entry "LFM3-VL-2B"). [vision-tower-reauthor.md](vision-tower-reauthor.md) covers the same contract for a window-attention ViT (MiniCPM-V-4.7).

## Re-write the tower for one grid

1. **Positions become constants.** At a fixed G the patch grid, the 2D rotary tables and every position are fixed: precompute the (G/16)² cos / sin rows. Bidirectional attention without a mask gives each token the same result in any token order, MLPs and norms work per token, and a depthwise convolution over the patch grid needs raster order anyway, so the whole tower can run in raster order. The projector's 2 × 2 merge (four strided slices concatenated on channels) then emits the source's merge-block order, which is the order of the `<image>` slots in the prompt.
2. **A temporal patchifier on a still picture is a Conv2d.** When the processor repeats the picture along time (T = 2), `W · [x; x] = (W[:, T=0] + W[:, T=1]) · x`: the patchifier Linear becomes Conv2d(3 → D, kernel 16, stride 16) with weight `W.reshape(D, 3, 2, 16, 16).sum(2)`.
3. **Take the u8 back before normalising.** The source processor computes `(u8 / 255 − 0.5) / 0.5`. Applied to the runtime's `u8 * (1/255)` in float32, the `− 0.5` cancels the leading bits (relative error 1.5e-5 at u8 = 128), and on a picture with flat grey regions a float32 re-write that normalised that input directly landed 13 to 18 times farther from a float64 reference than the source model's own float32 does (rms distance over the tower output and the projector output, at G = 512 and 768). `u = floor(x * 255 + 0.5)` recovers all 256 values exactly; then apply the processor's own formula, `(u − 127.5) / 127.5`. FLOOR builds on the Metal GPU delegate with the rest of the graph (ai-edge-litert 2.3.0).
4. **The converter folds the input step into the patch convolution.** The constants of `(u − 127.5) / 127.5` go into the convolution's weights (W / 127.5) and a bias, so the mean is subtracted after the weighted sum: on a flat grey patch the sum and the bias cancel to about 1/255 of their size (0.5 / 127.5), and 13.7 % of the non-zero folded weights fall below float16's smallest normal number. Centring before the FLOOR (`w = floor(x * 255 − 127.5)`, which is u8 − 128 for every u8, then `(w + 0.5) / 127.5`, the same pixel values) leaves only a small bias: against the source model's image features the float32 graph went from cosine 0.9999978 to 0.999999995 at the worst token. The centring also took the encoder with fp16 weights from 0.514 to 0.99972 (0.99973 with the power-of-two norm scales of the `fs` form in the cut-graph section below). Check the answers as well: in an LFM3-VL-2B file the `fs` encoder with fp16 weights moved two close answers on the Mac GPU (LiteRT-LM 0.18.1, the 23 picture questions of the model card's Accuracy section, whose harness is not in this repository: 20 of 23 answers kept the bfloat16 model's first 32 tokens with thinking off, against 22 for the published file and a bar of 21; a box coordinate off by one and a sign read in capitals), so the published files keep the default graph with fp32 encoder weights. `export_vision.py` writes the published form by default, the centred one with `--form u8c` and the `fs` form with `--form fs --ranges <ranges.json>` (`lfm3_vision.Opts`: `input_norm`, `rms_s`, `ln_s`), under the file names that `tower_tfl.py` and `tower_gpu.py` read, so each goes to a folder of its own: `convert_lfm3_vl.sh` packs whatever `OUT/tower` holds, and for `--form u8c` and `fs` the script refuses a folder that already holds vision graphs.

## Check the tower on its own, before any bundle

The fixture set is 12 pictures (8 drawn, 4 NASA photos); `lfm3vl_work/fixtures/fetch.sh` downloads the photos and draws the rest, and checks every file and pixel hash. The reference is the source model in Transformers on the CPU (`hf_ref.py --npy`: the projector output `feat` and the tower output `hid` for each picture at 512 × 512 and at 768 × 768; the float64 check uses both sizes).

```bash
bash lfm3vl_work/fixtures/fetch.sh <python with Pillow 13.0.0> write
HF_HUB_OFFLINE=1 HF_MODULES_CACHE=$PWD/hf_modules python lfm3vl_work/tools/hf_ref.py --src OUT/src --out REF --arms B512,B768 --dtype fp32 --npy --only none
python lfm3vl_work/tools/tower_tfl.py --tower-dir OUT/tower --ref-dir REF/ref_npy --out tower_tfl_g512.json
python lfm3vl_work/tools/tower_gpu.py --tower-dir OUT/tower --ref-dir REF/ref_npy --out tower_gpu_g512.json
HF_HUB_OFFLINE=1 python lfm3vl_work/tools/tower_f64.py --src OUT/src --ref-dir REF/ref_npy --images all --cross --out tower_f64.json
```

`OUT` is the output folder of `lfm3vl_work/convert_lfm3_vl.sh` after its `fetch` and `vision` steps (`OUT/src` the source snapshot, `OUT/tower` the four vision graphs). `--only none` names no question, so `hf_ref.py` writes the arrays and generates nothing; `HF_MODULES_CACHE` keeps the remote code it imports to the snapshot's own copy.

- **CPU** (`tower_tfl.py`): op histogram (no GATHER, GATHER_ND, FLEX, CUSTOM, STABLEHLO, BROADCAST_TO or RELU_0_TO_1), the largest tensor rank, and per-token cosine against `feat` for every encoder × adapter pair. LFM3-VL-2B: the fp32 encoder with either adapter 0.9999978 at the worst token over the 12 pictures; the fp16-weight encoder 0.514.
- **Mac GPU** (`tower_gpu.py`): a build on the Metal delegate with the GPU as the only accelerator (with GPU + CPU a graph the delegate only partly takes still builds), at fp32 and at fp16 precision. LFM3-VL-2B: both graphs built GPU-only; fp32 precision 0.999999, fp16 precision 0.244. The published files declare fp32 activations for both vision sections; the GPU's fp16 precision also failed with the input step centred (0.495) and with the norm scales of the `fs` form added (0.703).
- **float64** (`tower_f64.py`): the source's own modules in float64 (their float32 casts removed) are the truth. The verdict is taken on the flat-grey photo at both grid sizes and on two patch-embedding cases: the re-write in float64 must be within 1e-10 of the source in float64 (otherwise the re-write has an error), and its float32 within twice the source's own float32 distance from the truth. LFM3-VL-2B passed. With `--images all` (every picture at both sizes, 72 rows) the float64 forms stayed within 6.9e-12, and the float32 ratio had a median of 1.03 and a maximum of 2.11 (one picture's projector output, where the source's own float32 error is only 5.0e-6). `--variant v1`, the form that normalised the runtime's input directly, fails at 13 to 18 times on the flat-grey photo (exit code 2); `--cross` feeds the source's own float32 that same input step, and it lands 12.9 to 17.9 times away, so the excess comes from the input step, not from the re-write.

## Where the GPU's fp16 precision breaks it: cut graphs

`tower_cuts.py cuts` converts the encoder cut after the patch convolution, after its norm and after each of the 14 layers, and runs every cut on Metal at fp32 and at fp16 precision, one process per graph and precision (16 graphs in about 3 minutes on an M4 Max). The first cut whose fp16 column falls while its fp32 column stays at 1 is where float16 breaks. For LFM3-VL-2B it was the first op: fp16 against fp32 per-token cosine 0.361 at the patch convolution's output (nasa_radar; mean 0.969), while every fp32 cut matched host PyTorch at 0.999998 or better. That pointed at the folded input step of item 4, not at the norms. With the input step centred and power-of-two norm scales from `tower_cuts.py ranges` (`lfm3_vision.fp16_safe_scales`; the `fs` form, `tower_cuts.py cuts --form fs --ranges <ranges.json>`), the patch convolution reached 0.99994 and the break moved into the layers (0.999 at layer 2, 0.88 at layer 7, 0.67 at layer 12; in layers 2 to 11 the worst tokens were the same few positions of flat background in the right-hand column of the drawn pictures), so the end-to-end fp16 result stayed at 0.703.

Do not read Metal's fp16 from a host imitation. Running the whole tower in PyTorch float16 on the CPU (a half-precision run of the same modules; that script is not among the tools here) gave 0.996 for that form, and rounding only the outputs of one op class to float16 (linear, norm, convolution or residual) gave 0.9992 to 0.99997; Metal gave 0.703. The range pass explains part of it: in layers 0 to 3, 93 to 99.8 % of the squared inputs of the operator and feed-forward RMSNorms are below float16's smallest normal number, and the projector LayerNorm's row sum of squares (about 96,000) is above float16's largest value.

## The fixed grid has a cost; measure it

Run the source model on the native picture (the processor's smart_resize, which keeps the aspect ratio: 256 to 800 image tokens on these pictures) and on the G × G stretch (256 tokens at 512). For LFM3-VL-2B in float32 every scored answer stayed right (18 of 18) and the first 32 tokens stayed the same on 16 of 23 questions with thinking off (boxes moved a few units, descriptions were reworded); `hf_ref.py --arms N,B512 --dtype fp32` writes both runs with each answer's token ids and, for the 18 scored questions, whether it is right; compare the two runs' first 32 ids with `same32` in `lfm3vl_work/fixtures/score.py`. Say it on the model card, and resize photos to G × G with their orientation applied before the runtime stretches them (`lfm3vl_work/tools/lfm3_preprocess.py`).

A model that answers in coordinates can be bound to one input size: sweep the input size (patch grid h × w) on the original weights with synthetic buttons before any export. Mage-VL-Cowork hit 9 of 9 buttons at 1920 × 1088 (patch grid 68 × 120, what its own agent's 1920 × 1080 screenshots become in its processor) and 4 of 9 or fewer at six other sizes.
