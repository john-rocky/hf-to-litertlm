# Float16 arithmetic on the phone CPU (XNNPACK) for raw LiteRT graphs

LiteRT 2.3.0's CPU accelerator can run a graph in float16 arithmetic on an ARM phone through XNNPACK's FP16 flag. The `flags` value overwrites XNNPACK's default flags rather than adding to them (`litert_cpu_options.cc`); in the v2.3.0 source the default is 3 (QS8 | QU8), so float16 is 3 | 4 = 7 (with 4 alone the int8 kernels would be off). Set it with the `flags` key of the CPU accelerator's `xnnpack` options: `flags = 7` in the options TOML, `CpuOptions(xnnpack_flags=7)` in Python; the runner of nvidia/nemotron-3.5-asr-streaming-0.6b's conversion writes it from `--conf-xnn-flags 7`.

**The constant second input.** In LiteRT 2.3.0, XNNPACK in float16 mode refuses a BATCH_MATMUL whose second input is a constant: the delegate fails at prepare (`failed to delegate BATCH_MATMUL node #58`). A one-op graph with the same BATCH_MATMUL ([8, 4, 128] × [8, 128, 119]) and its second input fed as a graph input runs in float16 (`Batch Matrix Multiply (NC, PF16)`). (A constant float32 tensor stays float32 and is packed to float16 inside XNNPACK; with a float32 second input the batch matmul wants float32 on its first input and output too.) Attention with relative-position embeddings applies the position term this way, one matmul per layer.

**Fix: write the term as a FULLY_CONNECTED.** Fold the query projection into the position term so that each layer computes it as one fully connected layer on the attention's LayerNorm output. Fold the bias in with it and read the layer's input, not the query projection's output: `F.linear(hn, W_bd @ W_q, W_bd @ bias_v)`, where `hn` is the attention's LayerNorm output, `W_q` the query projection's weight, `bias_v` the position bias, and `W_bd` a block-diagonal matrix that holds each head's projected position embeddings. Two nearby forms made the converter duplicate the query projection and emit an extra 1024 × 1024 matrix multiplication per layer (292 FULLY_CONNECTED instead of 268): `F.linear(q + bias, W_bd)`, whose bias ADD was fused into a second query projection, and `F.linear(q, W_bd, W_bd @ bias)`, whose query projection output then had two consumers.

**Rescale the norms first.** Float16 arithmetic needs the graph's norms made fp16-safe (a power-of-two rescale per site from a range pass, as in [fp16-safe-norms.md](fp16-safe-norms.md)): the same rewritten graph with float32 weights and no LayerNorm rescale gave an empty transcript on all 82 utterances under flags 7.

Check the result in XNNPACK's profile (every kernel's datatype tag F16 — here `PF16`, `X16`, `F16`, none `F32` — in one XNNPACK partition; on the phone the delegate line read `Replacing 4090 out of 4093 node(s) … yielding 2 partitions`, the three cache concatenations at the graph's end staying on LiteRT's own kernel) and with a parity run.

On the rewritten conformer (float16 weights behind DEQUANTIZE, the int8 decoder on the CPU) the flag roughly halved the chunk time, one short run each: 53.072 ms with the flag against 107.648 ms without on a Galaxy S26 (6 threads, both runs in one sitting) and 84.038 against 176.418 ms on a Pixel 11 Pro (4 threads, the two runs in separate sittings, so the Pixel pair is indicative only).

**Check across processes.** Multi-threaded XNNPACK arithmetic can differ from one process to the next (float32 at 4 threads: the encoder outputs of two processes of the same graph and input differed by up to 5.6e-4; with run-time int8 activations one FLEURS Japanese utterance came out empty in one of two processes). Score the hardest set in three fresh processes before calling a form stable; here FLEURS Japanese under flags 7 gave CER 12.355 in each of three.
