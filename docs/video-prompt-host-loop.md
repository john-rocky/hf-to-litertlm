# A video prompt built in a host loop

LFM3-Omni-2B's Hugging Face processor reads a video with its soundtrack (`use_audio_in_video=True`) as groups of two frames, each group followed by the soundtrack rows of its time span. The `.litertlm` file has the parts for it — the vision encoder and adapter for one 512 × 512 picture (256 rows), the audio section, the embedder and the decoder — but LiteRT-LM 0.19.0's Conversation API cannot lay a video out that way: it encodes each audio item separately (`multimodal_processor_helper.cc`, lines 153–183), while the processor encodes the whole soundtrack once and splits its rows at the group boundaries. The two do not give the same rows: the audio section makes ceil(mel frames / 8) rows per call, so cutting the soundtrack at boundaries that are not multiples of 0.08 s gave 152 rows for 12 s where the processor gives 150. So the prompt is built in a host loop that calls the file's sections itself and copies the processor's arithmetic. These are the steps, and the traps, of an Android (Kotlin) loop that was checked against the processor.

1. **Frames in display order.** List the presentation timestamps of every video sample (Android `MediaExtractor`) and sort them; decode order differs from display order when the file has B-frames (the test files do). fps = the frame count over the track's duration (PyAV's `average_rate` gives the same value for these files); the processor rounds it to 6 decimals and uses it for both the timestamps and the audio boundaries.
2. **The processor's frame indices.** For N frames, n = min(max(int(N / fps × 2), 4), 384, N) (two frames per second), indices = `np.linspace(0, N − 1, n).round()`, which rounds half to even (Kotlin `Math.rint`, not `Math.round`); the last index is N − 1. Seek each group's first frame by its timestamp (`MediaMetadataRetriever.getFrameAtTime(pts, OPTION_CLOSEST)`), so the order never depends on how the encoder stored the frames.
3. **The stretch to 512 × 512, bit for bit.** The Python reference stretches each group's first frame with Pillow's `resize((512, 512), BICUBIC)`. A copy of Pillow 13's `Resample.c` must also copy its pass order: the horizontal pass first, unless the height loses more than twice as many pixels as the width, (h − oh) > 2 (w − ow); then the vertical pass goes first. Without that rule tall pictures differed by up to 20 levels (of 255).
4. **The soundtrack as the reference reads it.** The reference decodes it with `ffmpeg -ac 1 -ar 16000` and cuts it after the last non-zero sample. On Android, give `MediaCodec` a format without the `encoder-delay` and `encoder-padding` keys and cut them yourself (1,024 and 512 samples in the AAC test files); left in, the 12 s soundtrack made 151 rows instead of 150. Average the channels to mono, then resample like ffmpeg's default: a windowed sinc (Kaiser, β 9) with its cutoff at 0.97 of the lower rate's Nyquist frequency and 32 taps per side; past the start the signal is mirrored about its first sample, past the end it is mirrored after its last sample. Without the edge rule the edges differed by 1.1e-4.
5. **Encode the soundtrack once, split it at the group boundaries.** Run the audio section once on the whole soundtrack (up to 30 s; its mask marks the rows that are audio). Group 0 starts at row 0; group g ≥ 1 starts at round(index of its first frame / fps / 0.08), rounded half to even, capped at the row count and never below the previous start; the last group ends at the last row. In the processor's text each group is the timestamp `<{t} seconds>` (t = the mean of the group's two frame times, `"%.1f"`), its 256 picture rows (`<|video|>` placeholders) between `<|vision_start|>` and `<|vision_end|>`, then its `<|audio|>` rows.
6. **Check the copy on the desktop before the phone.** Run the app's Kotlin code on the desktop JVM against the Python reference. Here, after the two fixes above: the frame-index arithmetic equal to the processor's in 406 cases (the test files plus 400 random ones: 1 to 1,000 frames, 17 frame rates, 0 to 400 audio rows); the stretch byte-equal to Pillow on 40 pictures (the 24 frames the app sends and 16 random shapes: tall, wide, 4K, 1 pixel wide); the resampled soundtrack within 1.8e-7 of ffmpeg's from the same 48 kHz input, with the same length (192,000 samples) and the same 150 rows; the prompt's token ids equal for both test videos in both prompt forms.
