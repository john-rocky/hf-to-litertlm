# LiteRT-LM generic audio path — the contract a Confucius4 bundle has to meet (read from v0.17.1, 2026-10-02)

Source: `~/code/LiteRT-LM` tag `v0.17.1` (5e58e9a0), read with `git show v0.17.1:<path>`; Python API = litert-lm-api 0.17.1 in `~/venvs/lt0171run` (`litert_lm/*.py`). Line numbers are those of the tag. "Measured" = run on 2026-10-02 (the files named below); everything else is code reading. Starting point, from an earlier probe the same day: a metadata-only `generic_model` repack of the prompt-baked 5 s bundle failed with `Output tensor not found: features`, and an IO-renamed encoder with the prompt rows baked in failed with `598016 vs 1048576`.

## 1. Which encoder class runs, and what it must expose

- No `tf_lite_audio_adapter` section ⇒ the encoder is treated as **streaming**: `IsStreamingEncoder()` returns `true` for any encoder when `has_adapter` is false (`runtime/executor/audio_executor_utils.cc` l.42-54, used at l.69). The static encoder class is reachable only with an adapter. A static encoder is not needed here: the streaming class carries no state for an encoder without `feature_state*` / `prev_*` inputs (l.123-151; `audio_litert_compiled_model_executor.cc` l.446-466).
- Input: one of `audio`, `src_inputs`, `segment_values` (`audio_litert_compiled_model_executor.cc` l.98-99, checked in `AudioStreamingEncoder::Initialize` l.408-421). The runtime writes into it only; the only input mask it fills is `segment_mask` (l.405-407), so an input named `mask` would stay zero — none is used.
- Output: `features` is required (l.100, l.436-440); an output named `mask` is optional (l.101, l.441-443). The executor reads the mask as **uint8** (`GetDataAsVector<uint8_t>`, l.127-132) and takes `valid rows = last non-zero index + 1` (`GetValidCount`, l.117-125).
- Sequence lengths (`audio_executor_utils.cc` l.71-121): input length = `dims[-2]` of input 0 (no `mask` input), output length = `features.dims[-2]`; `audio_shrink_factor = input_len // output_len` (integer division, l.144-145); `streaming_chunk_size = input_len` (l.146-147).
- Valid rows per chunk (`EncodeInternal`, `audio_litert_compiled_model_executor.cc` l.818-827): from the output `mask` if present, else `ceil(valid input frames / shrink_factor)`. Without a mask a 30 s encoder with 3000 input frames and 390 output rows asks for `ceil(3000 / 7) = 429` rows of a 390-row buffer — the earlier probe's `598016 vs 1048576` failure was this computation (128 rows asked of a 73-row output). **So the encoder must emit `mask`** whenever `input_len` is not an exact multiple of `output_len`.
- Buffer sizes (`EncodeSpecsAndMasks` l.1056-1068, 1097-1117): the embedding buffer holds `N_chunks * ceil(window / shrink)` rows; a chunk writes `valid rows * D` floats from its own row offset. With mask = all ones: 30 s window `ceil(3000 / 7) = 429 >= 390`, 5 s window `ceil(500 / 7) = 72 >= 65`, so every chunk fits. The final tensor is cut to `total_valid_tokens` rows (l.1148-1221).
- Feature dtype: fp32 or fp16 `features` both read (l.873-889); ours is fp32.

## 2. What the runtime feeds the encoder (the audio preprocessor)

- Audio items reach the runtime as a file path or a base64 blob (`runtime/conversation/model_data_processor/data_utils.cc` `LoadItemData` l.30-57) and are decoded by miniaudio to **f32, mono only, resampled to `audio_sample_rate_hz`** (`support/preprocessor/audio_preprocessor_miniaudio.cc` `DecodeAudio` l.43-85; PCM16 becomes x / 32768). A pre-made tensor buffer is passed through untouched (l.134-142), but the Python `Content` API sends files (`Content.AudioFile`).
- `skip_mel_spectrogram_extraction: true` (`audio_preprocessor_miniaudio.cc` l.175-203): no scaling, no pre-emphasis, no FFT — the PCM is only cut into frames `GetFramedSegments` (`support/preprocessor/audio_preprocessor_utils.cc` l.121-149) and handed over as **[1, num_frames, audio_frame_length]**. With frame = hop = 160 the frames are consecutive, first frame = samples [0, 160) (initial `samples_to_next_step_ = frame_length`, `audio_preprocessor_miniaudio.h` l.119-124; `GetNextWindowOfSamples` l.90-119), and the last partial frame is zero-padded (`buffer_last_frame` is hard-coded false, `model_data_processor_factory.cc` l.398 → `audio_preprocessor_utils.cc` l.136-147).
- The built-in mel path (skip = false) cannot produce the Qwen3-ASR / Whisper log-mel, so it is not used:
  - frames are not centred (no reflect padding; frame t = samples [hop·t, hop·t + frame_length), `GetFramedSegments`), HF frames are centred (`torch.stft(center=True)`);
  - the filterbank is HTK-style — `FreqToMel(f) = 1127 ln(1 + f/700)` (`support/preprocessor/mel_filterbank.cc` l.223-224), triangles without Slaney area normalisation (l.76-120) — and is applied to the **magnitude** (`sqrt` of the power spectrum, l.171), HF uses the Slaney filterbank on the power spectrum;
  - the log is natural (`std::log`), with an optional floor and an optional fixed USM mean/std normalisation (`audio_preprocessor_utils.cc` l.190-221); there is no log10, no `max - 8` clamp and no `(x + 4) / 4`.
  Getting from that to the HF mel would need an approximation (frame offset, filterbank swap, normalisation without the per-clip max) — no numerical approximation was accepted for this conversion. What a near-miss mel costs was measured earlier with LiteRT-LM's omni ASR engine (its mel vs HF: max|Δ| 1.66; engine vs direct driver, same bundle: text equal on 109 of 155 clips).
- Defaults when a field is absent (`model_data_processor_factory.cc` l.379-398): 16 kHz, 1 channel, frame 512, hop 160, FFT 1024, input_scale 32768, pre-emphasis 0.97, 128 mels 125-7500 Hz, floor 1e-6, normalize true. The bundle sets every field it relies on.

## 3. Chunking, stride, overlap, flush

- Window = `streaming_chunk_size` = encoder input frames (3000 for 30 s, 500 for 5 s); overlap = 0 (it comes only from a `feature_state_0` input, `audio_executor_utils.cc` l.123-142); stride = window (`EncodeSpecsAndMasks` l.1023-1031).
- Buffering across calls is off by default (`audio_executor_settings.h` l.155 `audio_buffering_enabled_ = false`; the setter, l.129, is called only from tests in `runtime/` / `python/`), so `Encode` runs with `is_flush = true` (l.965-968): every frame is processed, the last chunk partially filled. Before each chunk the input buffer is zeroed (`ClearInputBuffers` l.484-505) and `chunk_len` frames are written, so a clip shorter than the window reaches the encoder **zero-padded to the window** — the same input as the wav zero-padded to 480,000 samples before the HF feature extractor, which is how the 30 s recipe was gated.
- A clip longer than the window becomes `ceil(frames / window)` chunks encoded independently and concatenated (l.1057-1120). Not run here (FLEURS max 29.3 s).

## 4. Prompt side

- `llm_model_type { generic_model { ... } }` is required for audio (`model_data_processor_factory.cc` `CreateGenericDataProcessorConfig` l.296-480; the `qwen3` type has no audio handling). Fields in `runtime/proto/llm_model_type.proto` l.40-148.
- Placeholder: the rendered template is split by `delimiter_regex`; a part matching `audio_token_regex` becomes `InputText(text before + audio_prefix + start_of_audio_token)` → `InputAudio` → optional `InputAudioEnd` (`add_audio_end`) → optional `audio_suffix`; text after the last placeholder is appended as `InputText` (`runtime/conversation/model_data_processor/multimodal_processor_helper.cc` l.116-188, l.200-203). With `<|audio_pad|>` as the placeholder and no prefix / suffix / audio-end, the vendor string `…<|audio_start|><|audio_pad|><|audio_end|>…` maps to text `…<|audio_start|>`, the audio embeddings, text `<|audio_end|><|im_end|>\n<|im_start|>assistant\n` + anything after it. Measured: prompt token count 405 = 9 + 390 + 6 (`out/r3_render_expected.json` tokenizer count vs the runtime's `token_count`).
- Render rule (`runtime/conversation/conversation.cc` l.288-323): the first message of a fresh conversation is rendered alone with `add_generation_prompt = true`; later messages must extend the previous render as a string (else `does not start with the previous rendered template string`). The bundle's jinja renders message by message (empty history → ''), so both cases hold.
- Content shape (`generic_data_processor.cc` l.96-112): a message with an audio item reaches the template as a list of typed items (`{"type": "audio", "path": …}`, `{"type": "text", "text": …}`); a lone text item reaches it as a string.
- Python 0.17.1: `Engine.create_conversation(…, system_message=, sampler_config=, max_output_tokens=, chat_template=)` (`litert_lm/engine.py` l.221-389; `chat_template` overrides the bundle jinja through `conversation_config_set_prompt_template`, l.306-309); `Conversation.send_message` returns a plain dict `{"role", "content": [{"type": "text", "text"}]}` (`conversation.py` l.274-346); `render_message_to_string` l.473-483; `token_count` is a property (l.501-509).

## 5. What this bundle does to meet it (`export_bundle_r3.py`)

- Encoder signature `encode`: input `audio` f32 [1, T, 160] (T = 3000 / 500), outputs `features` f32 [1, 390 / 65, 2048] and `mask` uint8 [1, 390 / 65] = all ones → every row of every chunk is prefilled, as in the (C) gate runs. The HF log-mel is computed in the graph (centred STFT as reflect pad + strided conv over the windowed DFT basis, the extractor's own Slaney filterbank, log10, `max - 8`, `(x + 4) / 4`), then litert-torch's Qwen3AsrEncoder body with the 104-token block-diagonal attention (encoder_window.py), no prompt rows.
- Metadata: `generic_model { audio_enabled, delimiter_regex "(<\|audio_pad\|>)", audio_token_regex "<\|audio_pad\|>", skip_mel_spectrogram_extraction, 16 kHz, 1 ch, frame = hop = 160, input_scale 1.0, add_audio_end false }`, stop tokens 151643 / 151645, max_num_tokens 1024 / 512, pad `<|endoftext|>`, jinja = the litert-torch Qwen3-ASR prompt per message (no system turn; system messages render nothing) with the user's text items after the generation prompt; `export_bundle_r3.py --prompt vendor` bakes the original repository's chat_template instead.
- Measured on released 0.17.1 (Python, Mac CPU): `Engine` + `create_conversation` + `send_message(Content.AudioFile)` work on the 5 example clips; the runtime's render equals the expected string in every case (audio only, system message, forced language, streaming prefix) for the shipped template (`out/r3_render_check_ship.json`) and for the vendor chat_template build (`out/r3_render_check.json`).

## Unverified

- Clips longer than one window (several chunks) — not run.
- Kotlin / Swift Conversation APIs — not run (same C++ data processor and executor; not measured).
- Non-16 kHz / compressed input decoded by miniaudio — not run here (the Fun-ASR-Nano conversion measured that resampled mp3 input changes 3 of 5 transcripts).
- Audio encoder on a GPU backend on Android — not run. On macOS (WebGPU) `create_conversation` fails with `BATCH_MATMUL: Not supported batched mat mul case: non-constant tensor`, so the audio encoder stays on the CPU.
